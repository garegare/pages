    LLMを用いた生成システムにおける正規化設計プラクティス

    2026年03月27日
    • LLM
    • 設計
    • アーキテクチャ
    • normalization

    概要

    LLM（大規模言語モデル）を活用した生成システムは、高い柔軟性と表現力を持つ一方で、その出力は必ずしも安定していない。

    入力・出力ともに構造が揺らぎやすく、そのままアプリケーションに組み込むと、さまざまな問題を引き起こす。

    • 出力フォーマットの揺れ
    • 意図しない構造変化
    • downstream処理との不整合
    • 再現性の低さ

    これらの問題に対処するために重要になるのが、「正規化レイヤー」という設計である。

    本記事では、LLMベースの生成システムにおける正規化設計の基本パターンを整理する。

    なぜ正規化が必要か

    LLMの出力は、本質的に以下の性質を持つ。

    • 自由度が高い
    • 文脈に依存して揺れる
    • 厳密な構造保証がない

    この特性により、実運用では次のような問題が発生する。

    • JSONを期待しているのに自然文で返る
    • 必須フィールドが欠落する
    • 意味は近いが異なる値が出る
    • 想定していないスキーマ構造になる

    したがって、

    LLMの出力をそのまま使ってはいけない。

    LLMの出力はあくまで「提案」であり、「確定したデータ」ではないという前提が必要になる。

    基本アーキテクチャ

    LLMを利用した生成システムでは、以下のような三層構造を採用するのが効果的である。

    [自由入力 / LLM出力]
        ↓
[中間表現（ゆるい構造）]
        ↓
[正規化（厳密構造）]
        ↓
[アプリケーションロジック]

    自由な生成と、厳密な構造保証を分離することが重要なポイントになる。

    中間表現の役割

    中間表現は、LLMの自由度を活かしつつ、後段で扱える形に受け止めるための層である。

    ここでは次のような設計を行う。

    • LLMには自由に生成させる
    • 構造はあえて「緩く」定義する
    • 欠損や表現の揺れを許容する

    例：

    {
  "role": "調査員",
  "entry": "依頼を受けて訪れた",
  "tone": "ミステリー",
  "scale": "中くらい"
}

    この段階では、厳密なenumや型制約は不要である。意味が通ることを優先し、表現の揺れは許容する。

    正規化レイヤーの役割

    正規化レイヤーでは、曖昧な中間表現を、厳密で扱いやすい構造へ変換する。

    値の正規化

    "中くらい" → Scale::Medium
"medium" → Scale::Medium
"中規模" → Scale::Medium

    構造の補完

    • 欠損値をデフォルトで補う
    • 不足フィールドを生成する

    不正値の処理

    • 無効な値を破棄
    • 近い値にマッピング
    • fallbackを適用

    型への変換

    struct NormalizedParams {
    scale: Scale,
    complexity: Complexity,
    entry_type: EntryType,
}

    設計原則

    原則1：LLM出力を信頼しない

    LLMは「提案」であり「確定値」ではない。

    原則2：構造の最終責任はコード側に持たせる

    • enum
    • 型
    • 制約

    は必ずコード側で保証する。

    原則3：テキストを正本にしない

    自然文は解釈が揺れるため、

    構造化データを正本とする。

    原則4：段階的に整形する

    一発で完全な構造を作ろうとしない。

    • generate（自由）
    • normalize（制約）
    • refine（調整）

    に分離する。

    原則5：分類軸は固定、語彙は拡張

    • 分類軸は固定
    • 表現は拡張可能

    よくある失敗パターン

    フル構造をLLMに生成させる

    • 出力が巨大になる
    • 破綻率が上がる

    enumを直接生成させる

    • 微妙に違う値が出る
    • validationが破綻する

    テキストから毎回再解釈する

    • 非決定的
    • パフォーマンス悪化

    正規化を後付けする

    • 設計が歪む
    • 不整合が増える

    良いパターン

    自由入力 → 正規化

    "港町の事件を調べる旅人"
        ↓
role = Traveler
entry_type = Observer
genre = Mystery

    生成と正規化の分離

    LLM → 中間JSON
Rust → 正規化

    組み合わせで表現力を出す

    EntryType + ContactKind + Strength

    応用領域

    この設計は以下に応用できる。

    • ストーリー生成
    • NPC生成
    • ユーザープロファイル
    • ゲーム状態管理
    • 対話システム
    • ワークフロー生成

    実践的な導入手順

    1. LLMの出力を観察する
    2. 揺れパターンを収集する
    3. 中間表現を定義する
    4. 正規化ルールを書く
    5. enum・型を設計する
    6. fallback戦略を決める

    まとめ

    LLMを使ったシステムでは、

    「生成」よりも「正規化」が重要になる。

    本質は、

    不安定な生成を、安定した構造に変換すること。

    そのためには、

    • 自由生成と構造保証の分離
    • 正規化レイヤーの明確化
    • 型による制約

    が不可欠となる。
